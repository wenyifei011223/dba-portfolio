# 03 mysqldump 逻辑备份 + binlog 时点恢复（PITR）

## 1. 实验环境

- 承袭笔记 01：VMware Workstation 17.5.2 + CentOS 7.9，MySQL 8.0.43，单库 `testdb`
- 提前开启 binlog：`log-bin=mysql-bin` + `server-id=1` + `binlog_format=ROW`（PITR 的前提）
- 备份工具：mysqldump（逻辑备份）+ mysqlbinlog（解析重放）
- 截图：S25–S29（均已上传 `mysql-ops/03-pitr/`）

## 2. 问题现象（踩坑记录，博客素材）

**坑 1：binlog 没开，PITR 无从谈起** — `SHOW VARIABLES LIKE 'log_bin'` 为 OFF 时，任何时点恢复都不可能。先改 `/etc/my.cnf` 加 `log-bin=mysql-bin`、`server-id=1`、`binlog_format=ROW`，`systemctl restart mysqld` 后确认为 ON、ROW。

**坑 2：位点取错，恢复完表又没了** — 最容易犯的错是取 `DROP TABLE` 事件自己的 `# at` 位点当 `--stop-position`，结果重放时把 DROP 也执行了，验证报 `ERROR 1146: Table 'testdb.t1' doesn't exist`。正确值是 **DROP 前最后一条完整事务（INSERT）的 `Xid` / `COMMIT` 行的 `end_log_pos`**，本次实测为 `444`。

**坑 3：`<STOP_POS>` 被 shell 当重定向** — 命令里的 `<STOP_POS>` 若忘记替换直接回车，shell 会把它当输入重定向，报语法错。必须先把占位符换成真实数字（本例 `444`）再执行。

**坑 4：binlog 被多次恢复污染，一堆 DROP 分不清** — 每导一次全量备份，binlog 就多一条 `DROP TABLE IF EXISTS t1 /*! generated by server */`，几次之后无法判断哪个才是误删事件。实验库直接 `RESET MASTER` 清空重做，位点最干净。`RESET MASTER` 生产环境禁用，面试要能讲清原因。

**坑 5：mysqldump 报 `A partial dump from a server that has GTIDs ...`** — 这是**正常警告**，不是错误。开了 GTID 的库做单库备份都会提示，PITR 场景保留 GTID 信息即可，不用加 `--set-gtid-purged=OFF`。

## 3. 操作过程

**第 1 步：开 binlog 并验证**

改 `/etc/my.cnf`，在 `[mysqld]` 下加：

```ini
log-bin=mysql-bin
server-id=1
binlog_format=ROW
```

```bash
systemctl restart mysqld
mysql -uroot -pNewPass@123 -e "SHOW VARIABLES LIKE 'log_bin'; SHOW VARIABLES LIKE 'binlog_format';"
```

预期 `log_bin=ON`、`binlog_format=ROW`。

![S25 binlog 前提证明](<../mysql-ops/03-pitr/S25-PITR 前提证明.jpg>)

**第 2 步：造数据 + 全量备份**

```bash
mkdir -p /backup
mysql -uroot -pNewPass@123 -e "CREATE DATABASE IF NOT EXISTS testdb; USE testdb; CREATE TABLE IF NOT EXISTS t1(id INT PRIMARY KEY, name VARCHAR(20)); INSERT INTO t1 VALUES(1,'a'),(2,'b');"
mysqldump --single-transaction --flush-logs --master-data=2 -uroot -pNewPass@123 testdb > /backup/testdb.sql
ls -lh /backup/testdb.sql
mysql -uroot -pNewPass@123 -e "SELECT * FROM testdb.t1;"     # 1,2
```

三个参数的意义：`--single-transaction` 对 InnoDB 做一致性快照**不加锁**；`--flush-logs` 滚动一个新 binlog，让备份后的变更进新文件；`--master-data=2` 把 CHANGE MASTER 坐标写成注释，恢复时对位点用。

![S26 造数据+全量备份](<../mysql-ops/03-pitr/S26-造数据 + 全量备份.jpg>)

**第 3 步：模拟备份后新增 + 误删表**

```bash
mysql -uroot -pNewPass@123 -e "USE testdb; INSERT INTO t1 VALUES(3,'c');"   -- 备份后的新增数据
mysql -uroot -pNewPass@123 -e "USE testdb; DROP TABLE t1;"                 -- 误删
mysql -uroot -pNewPass@123 -e "SHOW TABLES FROM testdb;"                   -- 空，表没了
```

**第 4 步：定位误删位点（关键，别用行号）**

```bash
SHOW BINARY LOGS;    -- 记下当前 binlog 文件名，如 mysql-bin.000002
```

```bash
mysqlbinlog --no-defaults -v --base64-output=DECODE-ROWS /var/lib/mysql/mysql-bin.000002 > /tmp/binlog.txt
grep -n -i -B 10 "DROP TABLE" /tmp/binlog.txt
```

在输出里找 `DROP TABLE t1` 上面的 `# at`（DROP 的起始位点），再往上找**上一条完整事务的 `Xid ... end_log_pos`**，那个数字才是 `--stop-position`。本次定位过程见 S27（画面里能看到 `# at 852` 的 DROP 事件和 `Xid = 64 end_log_pos 662`）；因中途多次导入做过 `RESET MASTER`，最终干净 binlog 里 INSERT(3,c) 的 `end_log_pos` 是 **444**，恢复按 444 执行。

![S27 binlog 位点定位](<../mysql-ops/03-pitr/S27-binlog-locate.jpg>)

> 官方与实战一致建议：**用 position（字节位点）而不是 `--stop-datetime`**——同一秒可能有多个事件，按时间切容易多放或漏放。

**第 5 步：恢复（先全量，再重放 binlog 到删除前）**

```bash
mysql -uroot -pNewPass@123 testdb < /backup/testdb.sql
mysqlbinlog --no-defaults --stop-position=444 /var/lib/mysql/mysql-bin.000002 | mysql -uroot -pNewPass@123
mysql -uroot -pNewPass@123 -e "SELECT * FROM testdb.t1;"    -- 验证 1,2,3
```

预期 `1 a / 2 b / 3 c` 全在——**备份后新增的 3,c 也被救回来了**，这正是 PITR 相对纯全量恢复的意义。

![S29 binlog 重放命令](<../mysql-ops/03-pitr/S29-binlog-replay.jpg>)

![S28 恢复结果 1,2,3](<../mysql-ops/03-pitr/S28-pitr-result.jpg>)

> 安全动作（面试加分）：整套恢复**先在隔离库/临时实例做**，别直接往生产导。止血第一步是 `SET GLOBAL read_only=ON` 回收写入，防止误操作区间被覆盖。

## 4. 关键概念说明（面试重点）

**① 什么是 PITR**

Point-In-Time Recovery，把数据库恢复到过去某个时间点/位点的状态。做法是「最近一次全量备份 + 备份之后到故障前的 binlog 重放」，能救回全量备份之后新增的数据。

**② 逻辑备份 vs 物理备份**

mysqldump 是逻辑备份，导出 SQL 语句，跨版本/跨平台友好、可单库单表，但备份恢复慢；XtraBackup（笔记 04）是物理备份，直接复制数据文件，速度快、适合大库，但版本绑定紧。

**③ 为什么用 position 不用 datetime**

同一秒内可能有多个事件，`--stop-datetime` 按时间切边界模糊，容易多放一个危险事件或漏放一个正常事务；字节位点精确唯一。

**④ `--single-transaction` 为什么不加锁**

它在一个事务里建立 InnoDB 一致性快照，备份期间不阻塞写入（前提是表引擎都是 InnoDB）；对比 `--lock-all-tables` 会锁全库。

## 5. 复盘 / 面试怎么讲

> 我先开启 binlog 并设为 ROW 格式，用 mysqldump 加 `--single-transaction --flush-logs --master-data=2` 做全量备份，然后模拟备份后新增一条数据、再误删表。
>
> 恢复分两步：先把全量备份导回，再用 mysqlbinlog 解析 binlog，定位到 DROP 前最后一条完整事务的字节位点，用 `--stop-position` 重放。我特意取 INSERT 事务的 `end_log_pos`（本例 444），而不是 DROP 自己的 `# at`——取错就会把 DROP 也重放，刚恢复的表又被删。最终 1、2、3 三行全部恢复，证明备份后新增的数据也救回来了。
>
> 中途踩了几个坑：`<STOP_POS>` 占位符没替换被 shell 当重定向、binlog 被多次导入污染后不好定位，我用 `RESET MASTER` 在实验库清空重做（生产禁用）。另外定点恢复我用 position 不用 datetime，因为同一秒多个事件按时间切不准。整套恢复我会在隔离库先验证再上生产，止血第一步是 `SET GLOBAL read_only=ON`。
